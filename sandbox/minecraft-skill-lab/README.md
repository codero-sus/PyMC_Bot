# Experimental isolated Minecraft skill lab

This is an opt-in, disposable trial of **untrusted** Mineflayer JavaScript. It is not a security certification and has not been validated against all sandbox escapes. Use a dedicated Linux machine or VM without valuable data, credentials or production services; keep its kernel, rootless Docker and gVisor patched. Docker alone or Node's `vm` is not a sufficient isolation boundary. Do not enable this on a machine where sandbox compromise would be unacceptable. Treat models, npm dependencies, images and the Minecraft server as supply-chain risks.

The PyMC Bot process must be able to access the **trusted rootless Docker daemon** for its own Linux user at `$XDG_RUNTIME_DIR/docker.sock`. Do not expose that daemon or the panel to untrusted users. The app itself can control that daemon; the generated code cannot access its socket. The lab requires gVisor configured as the Docker runtime `runsc`, cgroup v2 and daemon-reported memory, CPU quota and PID support. Rootless Docker resource limits require properly delegated cgroup controllers. A missing prerequisite fails closed. This configuration is intentionally not editable through the web API.

1. Obtain the **official Minecraft Java 26.1 server JAR** from Minecraft's official site, and put it at `sandbox/minecraft-skill-lab/server.jar`. The Docker build checks its expected SHA-1 `3872a7f07a1a595e651aef8b058dfc2bb3772f46`; independently verify the official download and digest as well. The JAR is not included or redistributed. The temporary server is subject to the [Minecraft EULA](https://aka.ms/MinecraftEULA).
2. From a trusted checkout, build locally: `docker build -t pymc-skill-lab:local sandbox/minecraft-skill-lab`. Building downloads base images and npm packages, so inspect/trust them first. Never use an untrusted image just because it has the lab label. Obtain the immutable local image ID: `docker image inspect pymc-skill-lab:local --format '{{.Id}}'`.
3. Only if you accept the Minecraft EULA, set `PYMC_BOT_LAB_EULA=accept` and `PYMC_BOT_LAB_IMAGE` to that exact `sha256:...` ID in the PyMC Bot server's environment; restart it with `XDG_RUNTIME_DIR` pointing to its rootless daemon. These settings are operator-controlled, not model-controlled. Without them no generated code runs.

Each attempted trial starts a fresh container with gVisor, network `none` (only its own loopback, for the temporary server), no host mounts or Docker socket, read-only image filesystem, an ephemeral size-limited `/tmp`, non-root UID, all capabilities dropped, no-new-privileges, and memory/CPU/PID/time/output limits. The image starts an offline, temporary 26.1 world and connects a local Mineflayer bot. It supplies no account credentials or host secrets. The container is removed after use on a best-effort basis; after a daemon crash or interrupted controller, check for and remove leftover `pymc-skill-lab-*` containers. Isolation and limits depend on the operator's runtime actually enforcing them. Per-process locking is not a system-wide quota; do not run multiple controller instances against the same host without additional limits.

The candidate and reporter share the container: hostile code can interfere with the server, fake completion, or exploit vulnerabilities in dependencies or the isolation stack. `completed_unverified` is therefore **not** a trusted test result, proof of functionality, or approval. Failed/blocked trials may be retried after fixing setup. A review record is scoped to the selected bot/server and exact source digest, is cleared on replacement or retrial, and never enables live deployment. There is no automated promotion or execution of generated JavaScript on a real server.
